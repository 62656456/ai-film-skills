# Future interface and causal-legibility system

Load this reference whenever a scene contains a cockpit, control room, visor, panel, display, mechanical indicator, alarm, FUI/HMI, operator authorization, when an isolated UI/HMI asset or interaction reference is requested, or when an existing image fails because its interface looks generic, decorative, retro by accident, or disconnected from the task. In a narrative/world frame, interface design follows the selected screenplay function, physics, spatial skeleton, and real user/system task and never repairs absent dramatic, relational, spatial, or physical evidence. An explicitly isolated UI/HMI asset follows its own testable system-model contract and does not need an invented external scene.

## Research boundary

Use human-factors standards to establish task logic, control/display grouping, feedback, degraded data, confirmation, and redundancy. Use official film-interface case studies only to learn how interfaces support actors, story beats, lenses, exposure, and on-set playback. Neither source class determines a franchise look, font, palette, or screen outline.

Current primary anchors:

- NASA crew-interface requirements: https://www.nasa.gov/reference/10-0-crew-interfaces-vol-2/
- NASA Appendix F display standard: https://www.nasa.gov/reference/appendix-f-vol-2/
- NASA Human Integration Design Handbook: https://www.nasa.gov/human-integration-design-handbook/
- NRC NUREG-0700 Revision 3: https://www.nrc.gov/reading-rm/doc-collections/nuregs/staff/sr0700/r3/index
- Territory Studio, functional screen graphics for *The Martian*: https://territorystudio.com/project/the-martian/
- Territory Studio, real-time on-set screen graphics: https://territorystudio.com/project/real-time-screengraphics/
- Territory Studio, research plus non-technical visual transformation for *Prometheus*: https://territorystudio.com/project/prometheus/

Treat the engineering sources as human-factors evidence and the studio sources as production evidence. Transfer mechanisms only. Do not copy any film's layout, iconography, typography, palette, animation, or hardware silhouette.

## Function-specific no-text evidence gate

For an interface inside a narrative or world frame, inherit the screenplay's selected visual contract and hide the title, prompt, captions, screen text, numbers, and symbols. At normal viewing size, the physical scene must already communicate the evidence required by that contract:

- action/decision: actor or responsible system, action, physical target, changed state, and script-supported consequence;
- discovery/information: observer, physical evidence, attention or understanding shift, and any intentionally withheld unknown;
- relationship/power: spatial control, access, gesture, exchange, or blockage and the relational response;
- establishing/atmosphere: location function, active world or causal emptiness, and latent condition or route;
- aftermath/transition: trace, implied cause, and affected new state;
- isolated non-interface asset/reference: identity, function, scale, applicable interfaces/relationships, and material/operating logic.

Use a three-second threshold only for beats whose source requires immediate action comprehension. A quiet discovery may unfold more slowly, and suspense may intentionally withhold meaning. If the essential contract depends on reading a screen, reblock the camera, body, object, mechanism, spatial relation, evidence, or consequence before adding UI.

UI may confirm, quantify, authorize, predict, translate an otherwise invisible variable, or control a real system. In a narrative/world frame it may not become the only proof that the beat happened. For every critical state the script requires the viewer to know, use at least two different evidence classes:

- body posture, gaze, hand or foot action;
- control position, mechanical geometry, load path, flow direction, or material motion;
- local light, sound-source proxy, thermal, pressure, fluid, deformation, or damage change;
- beneficiary, casualty, traffic, habitat, institution, or environmental consequence;
- interface state.

An interface-only state is not sufficient visual evidence in a narrative/world frame.

### Isolated UI/HMI asset exception

When the explicit deliverable is an isolated interface asset, screen family, interaction prototype, modality study, or UI diagnostic, do not invent a person, room, machine, beneficiary, failure, or distant consequence. Instead define and visibly test:

- one declared system model and task or information question;
- the human, nonhuman, collective, supervisory, or autonomous modality and authority relation, including `no operator` when correct;
- overview, task state, transition/response, confirmation only when critical, uncertainty/data validity, and degraded/fallback behavior only where applicable;
- mapping between information hierarchy and the declared system topology;
- at least two internal redundant cues for any critical state, such as shape plus position, topology plus motion, texture plus rhythm, or symbol plus spatial change; color or tiny text alone does not count;
- carrier/signal behavior and production constraints appropriate to a screen, physical prototype, animation, illustration, spatial/sonic/chemical interface, or another selected medium.

An isolated UI asset may be screen-only or nonvisual. It fails when it is decorative, cannot be exercised against the declared task/state model, or could move unchanged to an unrelated system.

## Interface-system card

Record only interfaces required by the current event or isolated asset; use agent-neutral fields and mark absent items `not applicable`:

- `agent and governance`: which human, nonhuman, collective, supervisory, autonomous, environmental, or `no operator` model senses, interprets, decides, confirms, overrides, adapts, or repairs when applicable;
- `task`: the one task, decision, or information question the interface supports in this frame;
- `world sensor`: what physical state is measured, with latency, uncertainty, and failure mode;
- `system topology`: real nodes, orientation, flows, boundaries, support/load/energy paths, and the display mapping that preserves them;
- `overview`: current system state and the abnormal region;
- `decision state`: current value or category, direction/trend, limit or remaining margin, predicted consequence, and data freshness;
- `input/control/governance`: the actual touch, pull, turn, brace, switch, authorization object, gesture, voice, gaze, neural/chemical signal, collective threshold, autonomous rule, or absence of user input;
- `confirmation`: the independent action required for critical, hazardous, irreversible, or destructive commands;
- `feedback`: immediate modality-appropriate acknowledgment plus real/declared system, organism, or environmental response; an isolated UI asset may keep both within its test model;
- `degraded mode`: stale/missing data, partial failure, manual fallback, and what remains trustworthy;
- `embodiment and environment`: applicable senses, reach or spatial access, restraint/support, vibration, acceleration, light or other signal conditions, glare/interference, corrosion, dust, pressure, heat, protective state, or nonhuman body relation;
- `production`: selected screen, physical prototype, sound/touch/chemical rig, animation, illustration, sensor rendering, material/signal behavior, performer/device cue when present, and typography/symbol boundary.

## Information and action hierarchy

Use only the hierarchy levels the task needs; these are screen-oriented examples, not a mandatory three-tier console:

1. **System overview**: one dominant topology showing where the event is occurring and which route, node, body, compartment, or population is affected.
2. **Current task/state**: the applicable target/question, state or trend, meaningful boundary, uncertainty, consequence, governance/authorization only when used, and response.
3. **Maintenance detail**: calibration, logs, component history, diagnostics, and exact values; keep secondary or off-camera unless the scene is specifically about diagnosis.

At normal image size, the selected primary information levels must read through large shapes, position, flow, changing area, mechanical state, or one coarse trace. Small text, pseudo-language, serial numbers, and precise decimals are set dressing only and must not carry the plot.

For any important number, show its object, unit or category, direction/trend, meaningful boundary, and consequence. A bare percentage, random code, or seven-segment value is not a future interface.

Mark stale, missing, estimated, or unavailable data through shape, texture, interruption, position, or explicit later-added label. Never let color alone carry critical meaning. Use at least one redundant cue such as line type, fill pattern, silhouette, icon, position, rhythm, or mechanical state.

## Interaction coupling and future form

Derive the interaction chain from the source's body, senses, task, environment, latency, authority, and failure mode. A useful generic chain is `sensor/state → presentation or cue → human, nonhuman, collective, or autonomous interpretation → input or authorization → effector/system → local and world feedback`, but show only the links the selected scene function needs.

Visual, tactile, auditory, gaze, gesture, voice, neural, chemical, nonhuman, distributed, and autonomous interfaces can all be valid when the source and mechanism support them. For a human manual interface, a visible `hand → eye → effector/system` triangle is one useful pattern, not a universal requirement. Whatever the modality:

- presentation, control, and system response agree with the real orientation, node, route, timing, and authority;
- selected nodes, branches, bodies, or states correspond to visible hardware, organism behavior, or world consequences;
- critical actions receive a modality-appropriate acknowledgment and an independently readable system post-state;
- the interface cannot be moved unchanged to another world or task without losing meaning.

Do not confuse `physical` with `retro`, or `interface` with `screen`. An interface can use a protected display, electronic ink, relief topology, mechanical state, tension/fluid channel, projected surface, visor, sound field, pressure wave, chemical pattern, body color/texture, collective motion, environmental trace, or a hybrid carrier. Choose it from embodiment, senses, environment, task, failure safety, lifecycle, energy, and governance—not from a generic sci-fi look.

Reject the default formula `small black rectangle + green/white monospaced text + isolated percentage + old wheel`. Use an old display only when the world's supply history, retrofit state, degradation, and agent/system workflow specifically require it.

When the source contains a critical or irreversible action, give it a modality-appropriate independent confirmation that the selected medium can reveal: a guarded or two-stage manual control, separate authorization object, dual-agent agreement, spatial/temporal gesture, audible challenge-response, distributed quorum, biological acknowledgment, autonomous interlock, or another non-actionable fictional control. After execution, leave an independently readable system or world post-state such as an empty slot, changed route, locked position, displaced marker, filled channel, unavailable option, altered organism response, or persistent environmental consequence.

## System-specific visual grammars

Derive the interface from what the system does. A screen that can move unchanged between worlds fails.

### Continuous field, liquid, membrane, or optical surface

Use only the applicable edge profile, contour, wavefront, curvature, interference, settling direction, capture boundary, confidence band, and local-loss cues. In a narrative/world frame, match the presentation to the real surface orientation and let real surface deformation remain the first proof. In an isolated interface asset, map those cues to the declared surface/state model without inventing an external scene.

### Distributed load, bridge, mecha, tether, or giant body

Use node order, support polygon, tension/compression direction, contact state, occupancy, transfer sequence, remaining support, and deformation. A physical load model, strain leaf, moving bead, or large mimic board may be more readable than a generic monitor.

### Energy, thermal, fluid, life-support, or civic allocation

When the screenplay actually contains a resource-allocation choice, use the applicable source, stored amount, spatial flow, branch allocation, losses, remaining envelope, beneficiary, and deprived branch. Make the interface topology follow the real system direction, and make the chosen branch plus affected body/place the primary physical evidence. For routine monitoring, discovery, ceremony, care, or a single-output system, do not invent a beneficiary, deprived district, countdown, or moral tradeoff.

### Biological or ecological system

Use pressure, circulation, respiration, tissue tension, fatigue, sensory orientation, contamination, and treatment path. Do not convert a living body into a generic humanoid health bar.

### Weapon, defense, or hazardous equipment

Keep it non-actionable. Emphasize authority, safe arc, exclusion zone, energy/heat budget, readiness, collateral constraint, degraded mode, and cease/abort state rather than construction, targeting algorithms, vulnerabilities, or real performance values.

## Live-action capture

- Build the control, bezel, glass, switch travel, mechanical indicator, relief topology, sight channel, or actor-contact surface practically when possible.
- Match screen playback to camera frame rate, exposure, viewing angle, lens, reflections, and actor timing. Keep display brightness below the level that would unrealistically light the whole face or cabin unless it is the named key source.
- Derive carrier and condition from environment and embodiment: matte glass, thick polycarbonate, coated transparent layers, ceramic insert, woven display, engraved scale, acoustic field, chemical marker, body pattern, spatial motion, or another supported medium. Add fingerprints, cleaning, corrosion, dust, heat, wear, or polish only where the source's use history produces them.
- For performed photographed interaction, give actors or practical devices a real cue matched to the same input and response seen in frame. For nonhuman, distributed, autonomous, illustration, or reference routes, reveal the equivalent timing through the selected sensory or system evidence rather than inventing a human movement.
- Generate coarse topology, blocks, paths, and state areas in the image; add precise typography and mission-critical text in post. Do not demand reliable tiny lettering from an image model.

## Prompt contract

When an interface is story-relevant, state the applicable items in this order. For an isolated UI/HMI asset, replace item 1 with its declared task/system-model test and omit external body/world consequences that the brief does not contain:

1. the selected no-text visual contract and its required evidence/information order;
2. the real system topology, orientation, branch, node, or surface state;
3. the responsible body, senses, collective, supervisory layer, or autonomous governance—and the applicable input/authorization/confirmation relation;
4. one dominant carrier or signaling medium and why this body, environment, task, and production route use it;
5. the matching interface topology and the source-required state, trend, or transition;
6. the immediate response plus independent system, organism, or world evidence at the distance the beat needs;
7. the carrier's applicable material or signal behavior, capture/readability limits, condition, degraded mode, and practical/post or illustration/animation split;
8. exclusions limited to likely failures.

Do not request a wall of UI, random data, dense technical text, generalized holograms, or a screen that explains an off-camera event. In a narrative/world frame, do not let UI cover the speculative phenomenon or source-required body/system action; in an isolated UI asset, protect the declared task and state model.

## Diagnosis and vetoes

Reject or revise if any answer is no:

1. In a narrative/world frame, with all UI text hidden, does the selected function-specific visual contract remain readable at the intended time? In an isolated UI/HMI asset, can the declared task and state hierarchy be exercised without depending on tiny text or decorative lore?
2. In a narrative/world frame, does each critical state have at least two different evidence classes? In an isolated UI/HMI asset, does it have at least two internal cues in the selected modality?
3. Is the main interface necessary for a real task rather than decorative future signaling?
4. Does it lie in the source-derived perception/input/governance/system/feedback relation and correspond to visible world evidence for a narrative frame, or to the declared test topology/state model for an isolated asset?
5. Does it show state, trend, margin/limit, predicted cost, confirmation, feedback, and data validity only to the degree the task needs?
6. Does the selected modality use redundant cues rather than color alone, and does any applicable degraded state remain distinguishable? Grayscale is a useful test for visual color interfaces, not for nonvisual modalities.
7. Is the primary hierarchy readable through coarse topology, spatial/temporal pattern, touch/sound/chemical relation, or another modality-appropriate structure rather than tiny generated text?
8. Do the applicable carrier/signaling medium, input/governance, material or signal behavior, visibility, condition, and fallback follow the environment, embodiment, task, and production route?
9. Would moving the interface unchanged to another system or world break its meaning? If not, redesign it.
10. Has the design avoided isolated black boxes, bare percentages, random seven-segment numbers, accidental retro styling, floating UI with no emitter, decorative blue/orange grids, and screens that light the entire set?

If a narrative/world frame is wrong, return to the screenplay contract, blocking, and spatial skeleton. Never use interface polish to conceal missing story evidence, a missing relationship, an absent state change, or an off-camera consequence. For an isolated UI/HMI asset, return to the declared task/system model and state coverage. Do not add a beneficiary, danger, failure, maintenance task, irreversible control, or persistent cost unless the source requires it.
